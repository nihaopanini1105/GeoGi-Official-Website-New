# GeoGi Research Center Autonomous OS v1.0

## 1. 目标

本工作流用于 GeoGi 官网研究中心的长期内容建设，核心目标不是“持续发文章”，而是持续建立 GeoGi 在 GEO、品牌 AI 可见度、品牌事实治理、AI 平台观察与行业应用上的公开知识资产。

默认工作方式：**自主完成，不要求用户逐步确认。**

只要任务是“继续研究中心 / 建设研究中心 / 补齐研究内容 / 更新研究中心”，执行者应直接完成从研究、选题、写作、审核、发布、QA、PR、合并到生产验证的完整闭环，不在中间阶段停下来等待“继续”。

## 2. 唯一允许中断并询问的情况

只有以下硬阻塞允许停止：

1. 需要新增或改变尚未确认的核心品牌事实，例如公司主体、正式品牌名、产品名称、法律资质、定价、合同承诺；
2. 医疗、法律、金融等高风险内容出现无法通过权威公开来源确认的关键事实；
3. 需要删除、覆盖或迁移现有正式资产，且会造成不可逆影响；
4. GitHub / Gitee / 生产环境权限、凭证、分支保护或部署链路阻塞，无法继续自动完成；
5. 官方来源之间存在实质冲突，无法在不猜测的前提下得出结论。

除上述情况外，不向用户索取过程确认。

## 3. 固定业务边界

- GeoGi 当前 GEO 检测、诊断、优化与复测服务聚焦中国市场。
- 当前正式观察平台：豆包、DeepSeek、腾讯元宝、通义千问、Kimi。
- 全球搜索、AI Search 与学术研究可作为方法和趋势参考，但不得把海外平台机制直接推断成国内平台未公开规则。
- 不声称掌握任何 AI 平台未公开排序、检索、推荐或引用算法。
- 不承诺“必然被推荐”“保证排名”“保证进入答案”。
- 不把单次回答、单次截图或单一模型结果写成长期排名或因果证明。

## 4. Research Center 的五层内容架构

### A. GEO 基础研究
回答用户最基础的问题：GEO 是什么、与 SEO/AEO 的关系、AI 搜索改变了什么、企业为什么需要关注。

### B. AI 平台研究
回答平台差异、跨平台观察、答案来源、搜索触发、引用与回答差异，但只讨论公开可观察现象。

### C. GeoGi 方法论
建立 GeoGi 自己可复核的方法资产：问题集、品牌事实、证据、指标、诊断、复测、优先级、实验设计、治理。

### D. 行业研究
围绕旅游、医美等重点行业，解释用户决策问题、信息风险、事实治理和 GEO 优先级。

### E. 年度研究报告
综合公开数据、年度平台变化、方法变化和 GeoGi 观察边界，不制造不存在的全国样本、市场份额或平台排名。

## 5. 自主生产流水线

### Stage 0 — 同步正式事实

先读取：

- `data/geogi-entity-facts.json`
- `data/research-index.json`
- `data/research-topic-map.json`
- `data/research-source-registry.json`
- 官网首页与已发布 Research 页面

任何文章都不得与 Canonical Brand Facts 冲突。

### Stage 1 — 内容缺口扫描

对现有内容做五维去重：

1. 标题与核心问题；
2. 目标读者与决策场景；
3. 核心论点；
4. 方法框架；
5. 结论与行动建议。

只有在“新增信息价值”明显时才创建新页面；能更新旧文的，不新建低价值重复页。

### Stage 2 — 选题评分

每个候选主题按 100 分制：

- 品牌实体建设价值 25
- 客户决策价值 20
- 搜索 / AI 问答需求 15
- GeoGi 方法差异化 15
- 可获得一手或权威证据 15
- 内链与主题集群价值 10

低于 70 分不进入正式写作；低于 80 分不优先发布。

### Stage 3 — 外部研究

优先顺序：

1. 中国政府 / 监管 / 国家级研究机构；
2. 平台官方文档与官方博客；
3. 原始论文、标准、研究数据集；
4. 高质量行业机构；
5. 媒体仅用于补充背景，不作为关键技术机制的唯一证据。

必须记录来源 URL、发布日期、访问日期、来源等级、支持的具体 Claim。

### Stage 4 — Evidence Pack

写作前先形成证据包：

- 已确认事实；
- GeoGi 自有方法定义；
- 可观察现象；
- 推论；
- 不确定项；
- 明确禁止写成事实的内容。

事实和推论必须在写作中区分。

### Stage 5 — Brief

每篇文章先明确：

- 用户问题；
- 目标读者；
- 搜索意图；
- GeoGi 要建立的实体关联；
- 文章独有结论；
- 主要证据；
- 应链接到哪些已发布页面；
- CTA 指向诊断、研究中心或行业方案。

### Stage 6 — Draft

推荐结构：

1. 先回答核心问题；
2. 解释为什么重要；
3. 给出 3–5 个关键观察；
4. 提供方法框架或可执行步骤；
5. 说明证据与边界；
6. 给出企业行动建议；
7. 相关阅读与官方来源。

文章必须是“非同质化内容”，不能只是改写公共常识。

### Stage 7 — Autonomous Review Gate

发布前自动完成九项审核：

1. **事实审核**：关键事实是否有可追溯来源；
2. **来源审核**：是否优先使用官方 / 原始资料；
3. **推论审核**：是否把推论伪装成事实；
4. **去重审核**：是否与现有 Research 高重复；
5. **品牌审核**：是否与 `geogi-entity-facts.json` 一致；
6. **合规审核**：是否存在保证、绝对化、医疗/法律越界；
7. **客户价值审核**：读完是否知道下一步怎么做；
8. **SEO/GEO 审核**：标题、描述、HTML、canonical、内链、Schema、可抓取文本是否完整；
9. **视觉与页面审核**：PC / Mobile、Logo、Footer、日期、分类、按钮与链接是否正常。

`review_status: approved` 代表以上审核已经完成，不代表必须等待用户人工点击确认。

### Stage 8 — 发布

正式发布源文件放在：

`content/research/<slug>.md`

通过发布脚本生成或更新：

- `insights/<slug>/index.html`
- `data/research-index.json`
- `insights/index.html`
- CollectionPage Schema
- `sitemap.xml`

### Stage 9 — QA

必须通过：

```bash
node --check scripts/publish-research.js
node --check assets/js/research-index.js
node scripts/validate-site.js
```

### Stage 10 — GitHub 发布闭环

固定流程：

```text
feature branch
→ 内容与页面构建
→ Website QA
→ PR
→ CI success
→ squash merge main
→ production/gitee-sync success
→ production/live-smoke success
```

只有 `production/gitee-sync` 与 `production/live-smoke` 同时为 success，才可对用户说“已经上线”。

## 6. 文章质量门槛

正式发布文章必须满足：

- 至少一个明确、独有的研究问题；
- 至少一个 GeoGi 方法框架、清单、模型或可执行流程；
- 涉及外部事实时至少 2 个可追溯来源，关键技术/监管事实优先一手来源；
- 不使用“AI 喜欢”“算法偏爱”等无法验证的人格化因果表达；
- 不使用“提高 X%”等未经当前场景验证的效果承诺；
- 不为制造页面数量而拆分近义词页面；
- 页面必须包含可见发布日期与更新时间；
- 至少 2 条站内相关阅读；
- 每个核心方法论页面都应该能反向强化“GeoGi = 中国市场品牌 GEO 诊断、优化与增长服务”的实体理解。

## 7. 内容更新机制

### 30 天检查

- 平台产品名、能力、入口是否变化；
- 外部链接是否失效；
- 统计数字是否有新版；
- 页面是否出现事实过期。

### 90 天方法复核

- 指标定义是否仍合理；
- 复测方式是否需要增加模型/版本字段；
- 新论文是否推翻旧判断；
- 是否出现更强一手来源。

### 年度更新

年度报告只在拥有足够公开证据时更新，不为了“年度感”虚构调研规模。

## 8. GeoGi 自身 GEO 品牌建设要求

Research Center 不只是获客内容，它同时承担品牌实体建设：

- 稳定重复 GeoGi 正式品牌名、业务边界和方法定义；
- 让“GeoGi / GEO / 品牌 AI 可见度 / 多平台观察 / 品牌事实治理 / 复测”形成清晰语义关联；
- 用方法论文章建立第一方权威解释；
- 用行业文章建立场景关联；
- 用年度报告建立持续研究者身份；
- 用透明证据和边界声明降低“GEO 玄学”风险。

## 9. 默认用户沟通方式

用户不需要回复“继续”。

执行完成后，只汇报最终结果：

- 新增 / 更新了哪些内容；
- PR 与 merge commit；
- QA 是否通过；
- `production/gitee-sync` 与 `production/live-smoke` 是否通过；
- 如果未上线，只说明硬阻塞，不把“已合并”说成“已上线”。
